# CLAUDE.md - Statutes Project Development Guide

This file provides Claude Code with project-specific context and guidance for developing this
project.

## Project Overview

**Project Name:** statutes
**Database:** statutes.db
**Purpose:** Searchable database of Singapore legislation from Singapore Statutes Online (SSO) —
current Acts with per-provision full text, version timeline metadata, and the as-published
gazette stream — served via Datasette on data.zeeker.sg. Sibling project to `zeeker-judgements`
(eLitigation), whose crawl scaffolding, two-phase pipeline, and disk-cache patterns this project
mirrors.

**Source:** https://sso.agc.gov.sg — Browse listings for the catalog (~525 current Acts; 523 on
the June 2026 fixtures), per-Act detail pages for text/timeline, and the AS PUBLISHED supplement
streams (SL Supplement, Acts Supplement) for daily change events.

**Spec:** `PRD.md` is the authoritative plan — read it before changing anything structural.
**Phase 0 findings:** `docs/phase0-findings.md` (formal report PENDING — generated by
`scripts/phase0_spike.py` in-window). The key verdicts are already encoded and fixture-tested in
the parser docstrings: the lazy-load replay is the full-text route (`?ViewType=Print` is an empty
shell — see `resources/parse_detail.py`), the `listing_stamp` `_` param is the change-detection
key (`resources/parse_listing.py`), and robots.txt declares crawl-delay 6
(`resources/sso_client.py`).

## Terms of Use compliance (HARD REQUIREMENTS — never relax these)

This project operates under SSO Terms of Use clause 13
(https://sso.agc.gov.sg/Terms-of-Use, "Use/Reproduction of Singapore legislation"). Every item
below is a build requirement:

1. **Extraction window — 03:00 to 07:00 Singapore Time only (cl 13(d)(i)).** Automated
   extraction from SSO runs only inside 03:00–07:00 SGT (19:00–23:00 UTC). Enforced in two
   places:
   - `resources/sso_window.py` — the runtime guard. `SSOClient` checks it **before every
     request**; outside the window it raises and the run checkpoints cleanly (state lives in
     the DB, so the next night resumes naturally). New requests stop at the **06:45 SGT hard
     stop** so in-flight work finishes inside the window.
   - The scheduling layer — the personal agent that runs `scripts/nightly.sh` sets its timer
     to start shortly after 03:00 SGT. The agent's timer is advisory: the runtime guard above
     is the authoritative enforcement, so a mistimed start degrades to a clean no-op, never a
     violation.
   - `STATUTES_IGNORE_WINDOW=1` is an escape hatch for **fixture/cached-file work only** —
     never set it for runs against the live site.
2. **Attribution (cl 13(a)).** `zeeker.toml` carries both required notices in the project
   description and license fields: (i) the legislation is subject to the copyright of the
   Singapore Government and is reproduced with the permission of the Attorney-General's
   Chambers under the SSO Terms of Use; (ii) users should check SSO
   (https://sso.agc.gov.sg) for the latest version of the legislation. Keep these intact in any
   metadata edit.
3. **No affiliation/endorsement claims (cl 13(c)(i)).** Metadata and UI copy must never imply
   AGC/SSO endorses or is affiliated with this project. The published description says so
   explicitly; phrase attribution as "reproduced with the permission of AGC under the SSO Terms
   of Use", nothing stronger.
4. **Honest, polite client (cl 13(c)(ii), 13(d)(ii)–(iii)).** User-Agent is always
   `ZeekerBot/1.0 (+https://data.zeeker.sg)` — no browser impersonation. Jittered 6s + 0-1s additive (robots.txt crawl-delay: 6)
   delay between requests, 3-attempt tenacity backoff whose waits are floored at the polite
   delay (a retry is still a request — it must never beat the crawl-delay), circuit breaker
   after 5 consecutive failures (`resources/sso_client.py`). The live-fetching scripts
   (`scripts/fetch_fixtures.py`, `scripts/phase0_spike.py`) hard-refuse to start if
   `STATUTES_IGNORE_WINDOW`/`STATUTES_NO_DELAY` are present in the environment. Never attempt
   to bypass any anti-bot or security measure SSO presents — if a route is blocked, that route
   is out.
5. **Accuracy responsibility (cl 13(b)).** We own accuracy. Every row links back to its SSO
   `source_url`; `current_as_at` and `extracted_at` are stored and surfaced; the published
   metadata carries the "check SSO for the latest version" notice; extraction tests against
   committed fixtures guard the parser.

## Cadence

**Tier 1 daily, permanently** — not just during backfill. New legislation lands on the
supplement streams almost every working day (~3 SL items/working day), so the nightly run:

1. **Stream ingestion** — page 1 of SL-Supp and Acts-Supp (current year, Number DESC); insert
   rows above the per-(series, year) high-water mark into `gazette_stream`; classify
   `event_kind`; resolve and invalidate amendment/revocation principals.
2. **Catalog reconciliation** — 2-request Acts listing diff (new ids / vanished ids / changed
   `listing_stamp` → invalidate).
3. **Queue drain** — extract works with `content_text IS NULL` until the per-run cap or the
   06:45 SGT hard stop, whichever first.

The run is cheap when nothing happened (4 requests, no extractions) and self-balancing on busy
gazette days. The ToU window constrains *when*, not *how often*. During the initial backfill
the queue is simply long: ~30–60 Acts/night → 525 Acts ≈ 2 weeks of nightly runs. Around 1 Jan,
poll both the old and new year's stream pages for a couple of weeks to catch the cursor
rollover.

**State management:** runner disk must be treated as ephemeral; the SQLite DB
round-tripped via `--sync-from-s3`/`deploy` is the only durable state (a persistent agent
machine keeps `statutes.db` locally, but nothing may *depend* on that). All cursors derive from
the DB (stream high-water mark, `content_text IS NULL` queue, stored `listing_stamp`) — no
judgements-style checkpoint JSON files for cursors. `.cache/` only needs to survive within one
build (it bridges zeeker's module reload between main-table and fragments phases). Within one
build zeeker calls `acts.fetch_data` TWICE (the second call only supplies fragments context and
is never inserted); `.cache/statutes_build_marker.json` (written at the start of every real run,
fresh < 6h) makes that second call issue zero requests and extract nothing — so the nightly
request/extraction budget is spent exactly once, and a stale marker never suppresses a real run
(see `resources/build_state.py`).

## Tables

| Table | What it holds | Keyed by |
|---|---|---|
| `acts` | Catalog of current Acts: one row per Work — listing metadata, status banner, full consolidated `content_text` once extracted | hash of `act:{shorthand}` |
| `acts_fragments` | One row per provision (section) of each Act's current expression — `provision_id`, heading, structure-preserving `content_text`, `structure_json` | hash of `{parent_id}:{provision_id}` |
| `act_versions` | Version timeline metadata: every point-in-time expression's validity date, amending Act, historical URLs (no historical text yet) | hash of `{act_id}:{valid_date}` |
| `gazette_stream` | Append-only event log of as-published SL/Acts Supplement items — the rolling-update substrate | hash of `{series}:{year}:{number_seq}` |

Full column descriptions live in `zeeker.toml` `[resource.*.columns]`. Identity rules (opaque
hash PKs, natural identifiers as content fields only, unique-index tripwires) are in PRD.md
"Identity and keys" — read it before touching any key derivation; changing a hash input is a
migration.

Shared helpers: `resources/ids.py` (hash derivations), `resources/sso_window.py` (window
guard), `resources/sso_client.py` (polite HTTP client + atomic cache writes).

## Environment variables

No env vars are required for correctness — defaults are production values. Knobs (all prefixed
`STATUTES_`):

| Env var | Default | What it controls |
|---|---|---|
| `STATUTES_IGNORE_WINDOW` | unset (`0`) | Set to `1` to bypass the 03:00–07:00 SGT window guard. **Fixture/cached-file work only — never against the live site.** |
| `STATUTES_NO_DELAY` | unset (`0`) | Set to `1` to skip the jittered inter-request delay (tests against fixtures only). |
| `STATUTES_DELAY_SECONDS` | `6.0` | Base sleep (s) between live requests. |
| `STATUTES_JITTER_SECONDS` | `1.0` | +/- jitter added to the base sleep. |
| `STATUTES_EXTRACT_ENABLED` | `1` | Set to `0` for discovery-only runs (skip full-text extraction). |
| `STATUTES_EXTRACT_MAX_PER_RUN` | `40` | Max Acts extracted per build. Deliberately generous — the 06:45 SGT hard stop is the true stop condition. |
| `STATUTES_MAX_FRAGMENT_CHARS` | `9000` | Oversize threshold: sections whose flattened text exceeds this split structurally into breadcrumbed child fragments. |

S3 deployment uses the standard zeeker env vars: `S3_BUCKET`, `AWS_ACCESS_KEY_ID`,
`AWS_SECRET_ACCESS_KEY`, `S3_ENDPOINT_URL` (zeeker auto-loads `.env` locally). No LLM/Jina
keys — AI summaries are deferred by decision (no `summary` columns).

## Development commands

All commands run through `uv`:

- `uv sync` — install dependencies
- `uv run zeeker build` — build the database from all resources (live extraction only works
  in-window; daytime development uses cached fixtures, never the live site)
- `uv run zeeker build --sync-from-s3 --setup-fts` — what the nightly run does: download the
  existing DB first, build incrementally, set up FTS indexes
- `uv run python scripts/sanity_checks.py` — post-build invariants (row counts never decrease
  vs `statutes.previous.db`, `has_content` ⇒ fragments, unique-index tripwires); `nightly.sh`
  runs this between build and deploy and refuses to deploy on failure
- `uv run zeeker deploy` / `uv run zeeker backup` — S3 deploy / dated archive
- `uv run pytest` — unit + fixture tests (includes the window-guard ToU tests)
- `uv run black --check .` and `uv run ruff check .` — formatting (line-length 100, py312) and
  linting; both must be clean

### Adding dependencies

`uv add package_name` (runtime) / `uv add --dev package_name` (dev). Conventions: `httpx` for
HTTP, `tenacity` for retries, `beautifulsoup4` + `lxml` for parsing, `click.echo` for progress.

## Deployment

**The personal agent owns scheduling; this repo owns the pipeline.** The agent invokes
`scripts/nightly.sh` on its own timer (start shortly after 03:00 SGT — the in-code window
guard is the authoritative enforcement, so a mistimed start is a clean no-op). The script:
snapshots `statutes.db` → `statutes.previous.db`, builds with `--sync-from-s3 --setup-fts`,
runs `scripts/sanity_checks.py` as a hard gate, and only then `zeeker deploy` — and only
when invoked with `--deploy`, which stays off until the first human review of extracted
data signs off. A non-zero exit from the script is the monitoring signal — the agent should
surface it before the next window. There are intentionally no GitHub Actions workflows in
this repo (legacy architecture; not used).
